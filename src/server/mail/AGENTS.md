> 루트 `AGENTS.md` 에서 떼어 낸 상세 참조다. 이 디렉터리 아래를 만질 때 읽는다.

## 발송 주소 · 대체 발송

**메일 발송 주소 · 대체 발송** (0135·0137): 이메일 열이 여럿일 때의 발송 주소 순서(`mailOrder`)와 반송·거부 시 다음 순위 주소로 한 통 더 보내는 대체 회차(`kind='fallback'`, cron `mailFallbackSweeper` — 새 Inngest 함수라 배포 뒤 수동 Resync)는 `lib/contacts/mail-email-order.ts` · `lib/mail/send-address.ts` · `server/mail/services/campaign-fallback.ts` 머리 주석이 정본이다(용어는 CONTEXT.md 「발송 주소」). 새로 "이 대상의 이메일"을 읽는 자리를 만들면 `field_type='email'` 을 직접 거르지 말고 `lib/mail/send-address`(규칙)·`server/read-models/send-address`(DB)를 쓸 것.

## 테스트 발송

템플릿 미리보기(`preview.sample`)와 「테스트 발송」(`preview.testSend`)은 설문의 테스트 모드가 켜져 있고 테스트 조사 대상자가 있으면 **첫 테스트 대상자**(`read-models/contact-sample` 의 `getFirstTestTargetSample`)의 값과 초대 링크를 쓴다 — 브라우저가 실데이터를 보는 중이어도 같다. 아니면 그 파티션의 첫 조사 대상 값이고, 테스트 발송의 초대 링크는 견본(`/i/__test__`)이다. **실제 조사 대상의 초대 링크를 테스트 메일에 넣지 말 것.** 수신거부 링크는 늘 견본 토큰이고, 게스트는 테스트 대상자를 쓰지 않는다. 용어는 CONTEXT.md 「테스트 발송」, 배선은 `server/mail/services/preview.ts` 머리 주석.

## 링크 클릭

수신자가 메일 본문의 링크를 누른 기록이다(용어·경계는 CONTEXT.md 「링크 클릭」, 결정 배경은 ADR 0042). 수신 상태와 별도이고 클릭 한 번이 `mail_link_clicks` 한 줄이다.

- **경로**: 웹훅 라우트가 `email.clicked` 알림의 클릭 정보를 `domain/link-click` 의 `parseResendClick` 으로 읽어 `processResendWebhookEvent` 에 넘긴다. 서비스는 상태 알림과 **같은 함수**(`lockRecipientForEvent` — 회차 행 → 수신자 행)로 수신자를 잠근 뒤 줄을 넣고 수신 상태를 「열람」으로 올린다(`applyClickEvent`). 장부 · 클릭 줄 · 전이 · 회차 집계가 한 트랜잭션이다. 잠금 순서를 따로 만들지 말 것 — 상태 알림과 엇갈린다.
- **링크 종류는 주소로 정한다**(`classifyClickedLink`): 앱 주소(`NEXT_PUBLIC_APP_URL`)와 같은 호스트의 `/survey/…` · `/i/…` 는 설문 링크, `/unsubscribe/…` 는 수신거부, 나머지는 그 밖의 링크. 발송 서비스는 글자 링크와 이미지 링크를 구분하지 않는다. 「그 설문」의 주소인지는 따지지 않는다.
- **주소는 그 밖의 링크만 저장한다.** 초대 링크·수신거부 링크의 주소에는 그 사람 전용 토큰이 들어 있다. IP 는 원문 없이 응답의 `ip_hash` 와 같은 식의 해시만 남긴다(`lib/duplicate-detection/salted-hash.server` — 식을 바꾸면 2단계에서 응답과 맞춰 볼 수 없다).
- **화면에 나가는 것은 링크 종류 · 첫 클릭 시각 · 그 밖의 링크 주소뿐이다.** IP 해시와 브라우저 정보는 어느 읽기 서비스·내보내기에도 싣지 않는다(2단계 재료). 로그·Sentry 에도 주소·IP·브라우저 정보를 싣지 않는다.
- **수신자당 200줄 상한**(`MAX_CLICKS_PER_RECIPIENT`): 수신자 행 잠금 아래에서 세고 넘으면 버린다(경고 로그). 메일 보안 장비의 자동 클릭을 추측해 걸러내지는 않는다 — ADR 0042.
- **회차 목록의 「클릭」은 집계 열이 아니라 조회 때 센다**(`campaigns-read` — 설문 링크를 누른 수신자 수, 보관된 수신자 제외). 집계 열을 만들지 말 것.
- **조사 대상 목록 · 단체 메일 위저드의 「링크 클릭」 열**(`system.link_click`): 칸·열 머리 필터·검색 조건·엑셀이 `lib/operations/contacts-filter-sql.server` 의 `linkClickStateExpr` 하나를 쓴다 — 눌렀다 / 받았지만 누르지 않았다 / 발송 이력 없음(NULL). 「발송 이력」의 범위는 수신 상황(`latestMailStatusExpr`)과 같아야 한다(보관 제외·같은 파티션). 설문 링크 클릭만 본다. 글자는 `filter-shared` 의 `linkClickLabel`·`LINK_CLICK_FILTER_OPTIONS` 한 곳이고 「응답」이라는 글자를 쓰지 않는다. 기존 설문의 열 스킴에는 읽을 때 「메일」 열 뒤로 끼운다(`contacts-format` 의 `withLinkClickColumn` — DB 는 고치지 않는다). 위저드는 고정 열 목록(`CAMPAIGN_HEADER_FILTER_COLUMNS`)에 있어 스킴과 무관하게 걸린다.
- **지난 회차를 채우지 않는다.** 구독을 켜기 전에 보낸 회차에는 기록이 없다 — 그 회차에서 누른 대상도 「없음」으로 보인다.
- **배포**: 마이그레이션 0170 을 먼저 적용하고, 앱 배포 **뒤**에 Resend 웹훅 구독에 `email.clicked` 를 더한다. 먼저 켜면 그 사이 알림은 장부에 「지원하지 않는 알림」으로만 적히고 다시 오지 않는다. Inngest Resync 없음.

## 회신 전달

보낸 사람 주소(`보낸이 계정@발송 전용 도메인`)로 들어온 메일을 회신 주소로 넘긴다 — 답장을 회신 주소가 아니라 보낸 사람 주소로 보내는 메일 시스템이 있어서다. 용어·규칙은 CONTEXT.md 「회신 전달」. 화면도 회신 기록도 없고, DB 쓰기는 웹훅 장부뿐이다(나가는 메일의 자리 줄, 답장 중계의 대상별 발송 기록 줄, 결과 줄).

- **경로**: 웹훅 라우트가 `email.received` 알림을 `services/reply-forward` 의 `forwardReceivedReply` 로 보낸다(수신자 상태 전이 `resend-webhook` 을 타지 않는다). 순수 규칙은 `domain/reply-forward`, 회신 주소 조회는 `services/reply-address-lookup`, 장부는 `services/reply-forward-ledger`. 담당자의 답장을 응답자에게 넘기는 답장 중계(아래)도 같은 진입점이고 규칙은 `domain/reply-relay`, 서명은 `services/reply-relay-signer`.
- **전달 주소는 DB 에 적힌 회신 주소에서만 나온다.** 받은 메일의 어떤 값(받는 사람·참조·답장 주소·본문)도 전달 주소가 되면 안 된다 — 그러면 누구나 우리 도메인으로 임의 주소에 메일을 보내게 된다. 받은 메일에서 쓰는 것은 「어느 보낸이 계정으로 왔는가」와 「누가 보냈는가」(어느 발송 회차의 회신 주소인지 고르는 재료)뿐이다. 답장 중계의 받는 사람(응답자)도 같은 원칙이다 — 받은 메일이 아니라 우리가 서명한 중계 주소에서만 나온다.
- **찾는 순서**: 보낸이 계정마다 먼저 응답자 주소로(`findReplyAddressByRespondent` — 그 계정 발송 회차 수신자의 발송 스냅샷 주소와 일치하는 것 가운데 가장 최근에 보낸 회차의 회신 주소 **한 곳**, 기간 제한 없음, 회신 주소가 비었거나 발송 전용 도메인인 회차는 건너뜀), 못 찾으면 계정 기준(`loadAccountReplyAddresses` — 최근 1년 회차의 회신 주소 ∪ 그 계정을 쓰는 삭제되지 않은 템플릿의 회신 주소 **전부**, 중복 없이 회차 것이 앞). 회차가 있다고 템플릿을 건너뛰지 말 것 — 같은 계정으로 새 설문의 템플릿을 만들어 「테스트 발송」만 한 단계에서는 그 회신 주소가 어느 회차에도 없다. 응답자 주소 비교에서 SQL 은 후보만 좁히고(`strpos`, 부분 문자열도 걸림) 판정은 발송과 같은 `splitEmailAddresses` 로 칸을 나눠 주소 하나하나와 정확히 한다 — LIKE 로 바꾸거나(`_` 가 와일드카드) 주소 나누기 규칙을 SQL 로 옮기지 말 것.
- **발송 전용 도메인의 주소는 전달 주소가 될 수 없다.** 회신 주소가 빈 옛 회차는 발송 때 보낸 사람 주소를 회신 주소로 썼다 — 그리로 넘기면 메일이 다시 들어와 고리가 된다. 같은 이유로 보낸 사람이 발송 전용 도메인이거나 전달 주소와 같은 도메인이면(회사 메일함 자동응답) 넘기지 않는다 — 서명이 맞는 중계 주소로 온 담당자의 답장은 이 판정에 오기 전에 답장 중계로 갈라진다.
- **고리 표식**: 전달 메일에 `X-Survey-Reply-Forward` 와 `Auto-Submitted: auto-forwarded` 헤더를 붙인다(`REPLY_FORWARD_HEADERS`). 받은 메일이 그 표식을 달고 있거나 배달 상태 통지(`multipart/report` 의 delivery-status, 보낸 사람이 `mailer-daemon`·`postmaster`)면 넘기지 않는다(`detectForwardLoop`) — 조회 응답의 보낸 사람·헤더로 먼저 보고, 원본을 푼 뒤 한 번 더 본다. 응답자의 부재중 자동응답(`auto-replied`)과 읽음 확인은 넘긴다 — 여기에 넣지 말 것.
- **SDK 의 전달 도우미(`emails.receiving.forward`)를 쓰지 말 것.** 답장 주소와 보낸 사람 이름을 넣지 못해 담당자의 「답장」이 응답자에게 가지 않는다. 원본을 내려받아 `postal-mime` 으로 직접 풀고 발송 API 로 보낸다. 원본은 글자가 아니라 바이트(`arrayBuffer`)로 읽는다.
- **장부 확인과 기록이 한 트랜잭션이 아니다.** 그 사이에 외부 호출(조회·내려받기·발송)이 끼기 때문이다 — 틈은 발송 멱등 키(`reply-forward/<받은 메일 id>`, 답장 중계는 `reply-relay/<받은 메일 id>` — 중계 대상이 여럿이면 통마다 `/to-<대상 조각>`)가 덮는다. 실패는 던져서 500 으로 답하고 장부에 적지 않는다(Resend 재시도가 처음부터 다시 한다). 넘기지 않은 것은 실패가 아니라 200 이다. 「같은 키에 내용이 다르다」 거절은 이미 보낸 것으로 보되 Sentry 경고(`reply_forward_idempotency_mismatch`)를 낸다 — 추정이라 사람이 확인한다. 「같은 알림이 처리 중」 거절(`concurrent_idempotent_requests`)은 장애가 아니라 표식을 달아 던진다(500, Sentry 이벤트 없음). **알려진 한계**: 발송 멱등 키는 24시간만 보관되는데 알림 재시도는 약 27시간 35분까지 이어진다 — 발송은 됐는데 결과 줄 기록이 그 하루 내내 실패하면(DB 가 하루 넘게 죽어야 한다) 마지막 재시도가 같은 메일을 한 통 더 보낸다. 한 통짜리(회신 전달·대상 하나인 답장 중계)는 이 틈을 그대로 둔다. 대상이 여럿인 답장 중계는 멱등 키에 기대지 않고 발송 기록 줄로 막는다(아래).
- **넘기지 않을 메일은 조회 전에 거른다**: 라우트가 알림에 실린 받는 주소·보낸 사람을 넘기고, 서비스는 받은 메일을 조회하기 전에 셋(발송 전용 도메인의 받는 주소 없음 · 보낸 사람이 발송 전용 도메인 · 쓴 적 없는 보낸이 계정)을 걸러 발송 서비스 API 를 한 번도 부르지 않는다. 알림 값은 거르는 데만 쓴다 — 넘길 메일의 판정과 전달 메일의 모양은 조회한 값으로 한다. 알림의 받는 주소가 빈 배열이면 「받는 주소 없음」이 아니라 「값 없음」이다(받은 메일의 받는 주소가 0개일 수는 없다) — 거르지 않고 조회한 값으로 판정한다.
- **시간 제한**: 조회·내려받기·발송마다 제한 시간이 있고(`REPLY_FORWARD_STEP_TIMEOUTS_MS` — SDK 가 중단 신호를 받지 않아 바깥에서 건다) 그 합이 웹훅 라우트의 `maxDuration` 안에 든다. 값을 바꾸면 `route-exports.test.ts` 가 대조한다. 모양을 바꿔 다시 보내는 발송은 제한 시간을 새로 받지 않는다 — 첨부를 실은 모양끼리 `send` 하나를, 첨부를 뺀 모양끼리 `sendWithoutAttachments` 하나를 나눠 쓴다(`createSendBudget`). 물러날 모양을 늘릴 때 모양마다 제한 시간을 주면 합이 `maxDuration` 을 넘는다. 한 받은 메일에서 여러 통이 나가는 답장 중계도 통들이 같은 몫을 나눠 쓴다 — 통마다 새로 주지 말 것.
- **받은 그대로 못 보내면 첨부 없이 본문과 안내만 넘긴다**(`deliver` — 회신 전달·답장 중계 공용). 인코딩한 첨부 합계 + 본문이 `FORWARD_SIZE_BUDGET_BYTES`(40MB 에서 여유를 둔 35MB)를 넘으면 처음부터, 한도 안쪽인데 발송 API 가 크기 초과로 거절하면 한 번 더. 다시 해도 결과가 같을 검증 계열 거절(400·422 — 막힌 파일 종류 등, `isPermanentRejection`)도 첨부 없이 한 번 물러나되 안내는 크기를 탓하지 않는다(「첨부 파일을 함께 전달하지 못했습니다」). 그것도 거절되면(또는 뺄 첨부가 없으면) 500 을 되풀이하지 않고 장부에 「넘기지 않음」으로 적고 Sentry 경고(`reply_forward_rejected`, 오류 이름·상태만)를 낸 뒤 200 으로 끝낸다 — 메일은 수신 목록에 남는다. **`isPermanentRejection` 을 넓히지 말 것**: 429·5xx·401·403(403 은 도메인 인증 문제인데 이름이 `validation_error` 다)이 들어가면 한도·설정 문제 동안 온 메일이 재시도 없이 버려진다. 본문 속 이미지도 함께 빠지고 안내의 목록에 든다. 파일 이름은 응답자가 정한 글자라 발송 요청과 안내 양쪽에서 줄바꿈·제어 문자를 걷어내고(비면 대체 이름), 안내에서는 HTML 이스케이프한다. **모양마다 멱등 키가 다르다**(`…/plain-from`·`…/no-attachments`, `replyForwardIdempotencyKey`) — 같은 키로 내용이 다른 요청은 거절된다. 크기 초과 거절의 오류 이름은 발송 서비스 문서에 없어 `isSizeRejection` 이 413 과 「크기를 말하는 검증 오류」 둘을 본다 — 실제 모양을 보면 그 함수 한 곳을 고친다.
- **내용 ID 는 본문 속 이미지에만 넘긴다**(`isInlineImage`): HTML 본문이 있고, 원본 풀기가 본문 속(related) 파트라고 했거나 본문이 그 `cid:` 를 실제로 참조할 때만. 내용 ID 가 붙었을 뿐인 일반 PDF 에 넘기면 받는 쪽 메일 프로그램이 첨부를 감춘다. 안내의 「본문 속 이미지」 표시도 같은 판정이다.
- **장부의 이벤트 종류 칸**: 결과 줄 `email.received:forwarded`(넘김) · `email.received:relayed`(답장 중계로 응답자에게 넘김) · `email.received:skipped`(넘기지 않음) — id 가 알림 id 라 「이미 처리한 알림」 판정에 쓰인다. 자리 줄 `email.received:slot` — 시간당 상한이 세는 줄이고 id 는 알림 id 에서 파생한다(`replyForwardSlotId` — 한 받은 메일에서 여러 통이 나가면 대상 조각이 붙어 통마다 한 줄). 발송 기록 줄 `email.received:relay-sent` — 답장 중계의 대상이 여럿일 때 대상마다 나간 직후에 적는 줄이고 id 는 알림 id + 대상 조각이다(`replyRelayDeliveryId`). 자리 줄·발송 기록 줄을 결과 줄과 같은 id·종류로 합치지 말 것 — 자리만 잡고(또는 일부 대상만 나가고) 실패한 알림이 처리된 알림으로 보여 재시도가 그 메일을 버린다. 장부에는 주소를 적지 않는다 — 대상은 주소에서 뽑은 조각(`relayTargetKey`)으로만 가리킨다. 배포 전에 온 알림은 기존 경로가 `email.received` 그대로 적는다.
- **시간당 상한**(`REPLY_FORWARD_HOURLY_CAP` 200통): 넘기기로 한 메일만, 원본을 내려받기 **전에** 자리를 잡는다(`reserveForwardSlot`). 세는 단위는 받은 메일이 아니라 **나가는 메일**이다 — 회신 전달은 한 통에 자리 하나, 답장 중계는 응답자마다 자리 하나(받은 메일 단위로 세면 자리 200개로 200통보다 많이 나간다). 짧은 트랜잭션 하나에서 `pg_advisory_xact_lock` 으로 줄을 세우고 최근 한 시간의 자리 줄을 센 뒤 상한 아래면 넣는다 — 세기와 넣기가 한 덩어리라 동시에 몰려도 상한을 넘지 않는다(외부 호출은 이 트랜잭션 밖). 발송 뒤에 적히는 결과 줄을 세는 방식으로 되돌리지 말 것. 같은 알림의 재시도는 자기 자리를 다시 쓰고, 자리는 돌려주지 않는다(발송이 실패해도 한 시간 동안 센다). 못 잡으면 `ReplyForwardCapExceeded` 를 던져 500 으로 답하고 결과 줄을 적지 않는다(Resend 재시도가 뒤로 미룬다). 넘기지 않는 메일은 자리를 잡지 않는다. Sentry 경고는 서비스가 내고 오류에 표식(`markSentryCaptured`)을 달아 라우트가 장애로 또 보내지 않는다.
- **전달 메일의 상태 알림**: 발송 태그 `kind=reply-forward` 로 가려낸다(`hasReplyForwardTag`). 중계 메일은 `kind=reply-relay`(`hasReplyRelayTag`)이고 똑같이 전이하지 않으며 닿지 못한 알림은 따로 경고한다(`operation: reply_relay_bounce`) — 담당자는 답장이 갔다고 믿으므로 이 경고가 유일한 신호다. `resend-webhook` 은 이 알림을 장부에만 적고 수신자 전이 경로를 타지 않는다 — 발송 회차 집계·메일 비용 집계가 회신 전달로 바뀌면 안 된다(`tests/integration/reply-forward-safeguards.realdb.test.ts` 가 못박는다). `email.bounced`·`email.failed`·`email.suppressed`·`email.complained` 는 Sentry 경고(`operation: reply_forward_bounce`, 종류는 태그 `eventType`)이고 나머지는 조용히 지나간다 — 한 번 반송된 회신 주소는 그 뒤로 반송이 아니라 `suppressed` 로만 알려 온다. 전달 메일의 `kind` 태그를 빼거나 값을 바꾸면 이 분기가 죽는다.
- **답장 중계**(CONTEXT.md 「답장 중계」): 회사 메일은 「답장」 때 답장 주소를 무시하고 보낸 사람 주소로 보낸다. 그래서 전달 메일의 보낸 사람 주소는 중계 주소(`계정+<응답자 주소의 @ 앞>=<도메인>=<서명>@발송 전용 도메인`, `buildRelayLocalPart`)이고, 받는 주소에 서명이 맞는 중계 주소가 있으면서 보낸 사람이 그 계정의 회사 도메인이고 보낸 사람의 발신 인증을 통과한 메일은 그 주소가 가리키는 응답자에게 넘긴다(`relayStaffReply`). 이 갈림은 회신 전달의 전달 주소 찾기·회사 도메인 판정보다 **먼저** 한다 — 갈라지지 않은 메일(중계 주소가 없거나 서명이 틀림, 회사 밖에서 옴)만 꼬리를 무시하고 그 판정으로 간다. DB 에 응답자 주소를 저장하지 않는다 — 주소가 스스로 말하고 서명이 보증한다.
  - **받는 사람은 서명이 맞는 중계 주소에서만 나온다**(`parseRelayAddress`·`extractRelayTargets`). 서명을 보지 않고 꼬리의 주소를 읽거나 받은 메일의 받는 사람·참조·답장 주소를 쓰면 누구나 우리 도메인으로 임의 주소에 메일을 보낸다. 서명이 틀린 주소는 꼬리를 무시하고 계정만 본다.
  - **「회사 도메인에서 왔는가」는 그 중계 주소의 계정의 계정 기준 회신 주소로 본다**(`keepCompanyRelayTargets` — `loadAccountReplyAddresses`, 중계 길로 갈지와 어느 대상을 남길지 둘 다). 회신 전달의 전달 주소(보낸 사람 주소로 좁힌 것, `findReplyAddressByRespondent`)를 재료로 쓰지 말 것 — 담당자가 같은 계정의 어느 회차(테스트 회차 등) 수신자였고 그 회차의 회신 주소가 다른 도메인이면, 담당자의 답장이 중계되지 않고 그 다른 회신 주소로 회신 전달된다. 판정은 계정마다 한다 — 받는 주소의 계정을 합친 채로 보면, 회신 주소를 외부 메일로 적은 다른 계정을 함께 넣어 그 외부 도메인의 누구나 중계를 연다. 계정 기준 회신 주소는 한 요청 안에서 계정마다 한 번만 읽는다(`createAccountReplyLoader`).
  - **보낸 사람의 발신 인증(DMARC)을 통과한 메일만 중계한다**(`readDmarcVerdict` — 조회 응답의 `authentication.dmarc === 'pass'`). 보낸 사람 도메인은 꾸밀 수 있는 헤더 값이라, 인증 없이 넘기면 서명된 중계 주소를 손에 넣은 외부인이 보낸 사람을 회사 주소로 꾸며 그 응답자에게 우리 도메인 이름으로 임의 내용을 보낸다. 통과가 아니면(`fail`·`gray`·`processing_failed`·`unknown`·칸 없음·null) 자리를 잡기 전·원본을 내려받기 전에 「넘기지 않음」(`relay_unauthenticated`)으로 끝내고 Sentry 경고(`reply_relay_unauthenticated`, 태그 `dmarc` 값만)를 낸다 — 회신 전달로 떨어뜨리지 말 것(사칭 메일이 담당자 메일함으로 간다). 재료는 조회 응답의 `authentication` 칸뿐이다(받는 메일 서버가 계산한 값, 설치된 SDK 타입에 없어 넓혀 읽는다) — 메일의 `Authentication-Results` 헤더는 보낸 사람이 넣을 수 있으니 쓰지 말 것. 회신 전달(응답자의 답장)에는 이 판정을 걸지 말 것 — 발신 설정이 허술한 옛 메일 시스템의 답장을 받으려는 기능이다.
  - **응답자마다 한 통씩 보낸다 — 받는 사람은 언제나 한 명이다**(`buildRelayMail` 이 주소 하나만 받는다). 여럿을 한 통에 모으면 응답자끼리 서로의 주소를 본다(담당자가 숨은 참조로 넣었어도). 대상이 여럿이면 통마다 멱등 키에 대상 조각이 붙는다(`relayTargetKey` — 응답자 주소에서 뽑은 값, 주소도 순번도 아니다). 조각을 붙일지는 **서명이 맞는 중계 주소 수**로 정한다(회사 도메인 판정으로 걸러 낸 뒤의 수가 아니다 — 그 판정의 재료는 재시도 사이에 바뀔 수 있어 같은 대상의 키가 달라진다). 도중에 실패하면 던지고(500, 결과 줄 없음) 재시도가 처음부터 다시 돈다 — 통의 내용을 재시도마다 달라지게 만들지 말 것(발송 기록을 못 적은 대상은 같은 키·같은 내용으로 다시 간다). **자리와 발송 기록은 나가는 메일 단위다**: 통마다 보내기 직전에 자리를 잡고(첫 통의 자리는 원본 내려받기 전, 못 잡은 대상에서 멈추고 500), 나간 직후(「이미 보냄」 포함) 그 대상의 발송 기록 줄을 적는다(`recordRelayDelivery`). 재시도는 발송 전에 그 줄을 보고(`loadDeliveredRelayTargets`) 이미 나간 대상은 발송 서비스도 부르지 않고 자리도 다시 잡지 않는다 — 멱등 키에만 기대면 한 대상이 계속 실패할 때 키 보관 기간(24시간)이 지난 마지막 재시도가 이미 나간 대상에게 한 통 더 보낸다. 끝내 거절된 대상은 발송 기록이 없다(나간 메일이 없다). 장부의 결과 줄은 받은 메일 한 통에 하나다. 서명이 맞는 중계 주소가 하나뿐이면 회신 전달과 같다(자리 하나, 발송 기록 줄 없음). 일부 대상만 끝내 거절되면 나머지는 보내고 「중계」로 적되 같은 경고(`reply_relay_rejected`, `rejectedCount`)를 낸다. 로그의 `relayCount` 는 보낸 통 수다.
  - **서명 키는 `RESEND_WEBHOOK_SECRET` 이다**(새 환경 변수 없음). 이 값을 바꾸면 이미 나간 전달 메일의 중계 주소가 전부 죽는다 — 그 메일에 한 「답장」은 회사 도메인에서 온 메일로 걸러져 응답자에게 가지 않는다. 서명의 재료·길이(`relaySignatureMaterial`·10자)를 바꿔도 같다.
  - **보낸이 계정을 뽑는 자리는 `+` 뒤를 떼고 본다**(`extractSenderAccounts`). 안 그러면 중계 주소로 온 메일이 「쓴 적 없는 보낸이 계정」으로 조회 전에 버려진다. 회사 밖에서 중계 주소로 온 메일은 꼬리를 무시하고 그 계정의 회신 전달로 간다.
  - **자동으로 만들어진 메일은 중계하지 않는다**(`isAutoGeneratedMail` — `Auto-Submitted` 가 `no` 가 아님 · `X-Autoreply`·`X-Autorespond` · `Precedence: bulk|junk|auto_reply`). 회사 메일함의 부재중 자동응답이 응답자에게 가고 두 자동응답이 서로 주고받는다. 회신 전달 쪽(응답자의 자동응답은 넘긴다)에는 이 판정을 쓰지 말 것. 중계 메일에는 `Auto-Submitted` 를 붙이지 않는다(사람이 쓴 답장이다).
  - **중계 주소를 못 쓰면 안내 한 줄**: `@` 앞이 64자를 넘거나 옮길 수 없는 글자가 있으면, 또는 발송 서비스가 중계 주소를 쓴 모양을 검증 거절하면(Sentry 경고 `reply_forward_relay_address_rejected`) 보낸이 계정 주소로 보내고 본문 맨 위에 「받는 사람을 직접 넣어 달라」를 붙인다(`account_with_guide`). 물러나는 순서는 중계 주소 → 보낸이 계정 주소 + 안내 → 첨부 없음이고, 크기 초과는 보낸 사람 주소를 두고 첨부만 뺀다.
  - 시간당 자리·큰 첨부·발송 거절·멱등 처리는 회신 전달과 같은 장치다(자리는 한 상한을 나눠 쓴다). 첨부 안내의 마지막 줄만 응답자용이다 — 발송 서비스의 수신 목록을 말하지 않는다.
- **로그·오류 문구·Sentry 에 주소·이름·제목·본문·파일 이름을 싣지 않는다.** 발송 서비스가 돌려준 오류 문구도 주소를 담을 수 있어 분류값(`error.name`·상태 코드)만 옮긴다. 웹훅 라우트가 서비스에 넘기는 받는 주소·보낸 사람도 로그에는 싣지 않는다(식별자만). 원본 내려받기 주소는 서명된 URL 이라 그 요청만 `Sentry.suppressTracing` 안에서 보낸다 — Sentry 는 나가는 요청의 쿼리를 breadcrumb·span 에 싣고 기본 가림 목록에 서명 칸(`X-Amz-Signature`)이 없다.
- **배포**: 마이그레이션·Inngest Resync 없음. 앱 배포 뒤 Resend 웹훅 구독에 `email.received` 를 더하고, `email.failed`·`email.suppressed`·`email.complained` 가 구독에 들어 있는지 본다(전달 메일이 닿지 못했다는 경고의 재료). **`email.received` 는 운영 웹훅 엔드포인트 하나에만 구독한다** — staging 엔드포인트가 함께 구독하면 같은 받은 메일을 두 환경이 처리하고, 중계 주소의 서명이 환경마다(서명 키가 달라) 갈려 담당자의 답장이 조용히 걸러진다.
