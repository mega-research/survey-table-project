## 발송 주소 · 대체 발송

**메일 발송 주소 · 대체 발송** (0135·0137): 이메일 열이 여럿일 때의 발송 주소 순서(`mailOrder`)와 반송·거부 시 다음 순위 주소로 한 통 더 보내는 대체 회차(`kind='fallback'`, cron `mailFallbackSweeper` — 새 Inngest 함수라 배포 뒤 수동 Resync)는 CONTEXT.md 「발송 주소」가 정본이다. 새로 "이 대상의 이메일"을 읽는 자리를 만들면 `field_type='email'` 을 직접 거르지 말고 `lib/mail/send-address`(규칙)·`server/read-models/send-address`(DB)를 쓸 것.

## 테스트 발송

템플릿 미리보기(`preview.sample`)와 「테스트 발송」(`preview.testSend`)은 설문의 테스트 모드가 켜져 있고 테스트 조사 대상자가 있으면 **첫 테스트 대상자**(`read-models/contact-sample` 의 `getFirstTestTargetSample`)의 값과 초대 링크를 쓴다 — 브라우저가 실데이터를 보는 중이어도 같다. 아니면 그 파티션의 첫 조사 대상 값이고, 테스트 발송의 초대 링크는 견본(`/i/__test__`)이다. **실제 조사 대상의 초대 링크를 테스트 메일에 넣지 말 것.** 수신거부 링크는 늘 견본 토큰이고, 게스트는 테스트 대상자를 쓰지 않는다. 용어·규칙은 CONTEXT.md 「테스트 발송」.

## 회신 전달

보낸 사람 주소(`보낸이 계정@발송 전용 도메인`)로 들어온 메일을 회신 주소로 넘긴다 — 답장을 회신 주소가 아니라 보낸 사람 주소로 보내는 메일 시스템이 있어서다. 용어·규칙은 CONTEXT.md 「회신 전달」. 화면도 회신 기록도 없고, DB 쓰기는 웹훅 장부 한 줄뿐이다.

- **경로**: 웹훅 라우트가 `email.received` 알림을 `services/reply-forward` 의 `forwardReceivedReply` 로 보낸다(수신자 상태 전이 `resend-webhook` 을 타지 않는다). 순수 규칙은 `domain/reply-forward`, 회신 주소 조회는 `services/reply-address-lookup`, 장부는 `services/reply-forward-ledger`.
- **전달 주소는 DB 에 적힌 회신 주소에서만 나온다.** 받은 메일의 어떤 값(받는 사람·참조·답장 주소·본문)도 전달 주소가 되면 안 된다 — 그러면 누구나 우리 도메인으로 임의 주소에 메일을 보내게 된다. 받은 메일에서 쓰는 것은 「어느 보낸이 계정으로 왔는가」와 「누가 보냈는가」(어느 발송 회차의 회신 주소인지 고르는 재료)뿐이다.
- **찾는 순서**: 보낸이 계정마다 먼저 응답자 주소로(`findReplyAddressByRespondent` — 그 계정 발송 회차 수신자의 발송 스냅샷 주소와 일치하는 것 가운데 가장 최근에 보낸 회차의 회신 주소 **한 곳**, 기간 제한 없음, 회신 주소가 비었거나 발송 전용 도메인인 회차는 건너뜀), 못 찾으면 계정 기준(`loadAccountReplyAddresses` — 최근 1년 회차의 회신 주소 **전부**, 없으면 템플릿). 응답자 주소 비교에서 SQL 은 후보만 좁히고(`strpos`, 부분 문자열도 걸림) 판정은 발송과 같은 `splitEmailAddresses` 로 칸을 나눠 주소 하나하나와 정확히 한다 — LIKE 로 바꾸거나(`_` 가 와일드카드) 주소 나누기 규칙을 SQL 로 옮기지 말 것.
- **발송 전용 도메인의 주소는 전달 주소가 될 수 없다.** 회신 주소가 빈 옛 회차는 발송 때 보낸 사람 주소를 회신 주소로 썼다 — 그리로 넘기면 메일이 다시 들어와 고리가 된다. 같은 이유로 보낸 사람이 발송 전용 도메인이거나 전달 주소와 같은 도메인이면(회사 메일함 자동응답) 넘기지 않는다.
- **SDK 의 전달 도우미(`emails.receiving.forward`)를 쓰지 말 것.** 답장 주소와 보낸 사람 이름을 넣지 못해 담당자의 「답장」이 응답자에게 가지 않는다. 원본을 내려받아 `postal-mime` 으로 직접 풀고 발송 API 로 보낸다. 원본은 글자가 아니라 바이트(`arrayBuffer`)로 읽는다.
- **장부 확인과 기록이 한 트랜잭션이 아니다.** 그 사이에 외부 호출(조회·내려받기·발송)이 끼기 때문이다 — 틈은 발송 멱등 키(`reply-forward/<받은 메일 id>`)가 덮는다. 실패는 던져서 500 으로 답하고 장부에 적지 않는다(Resend 재시도가 처음부터 다시 한다). 넘기지 않은 것은 실패가 아니라 200 이다.
- **첨부가 발송 한도를 넘으면 첨부 없이 본문과 안내만 넘긴다**(`deliverForwardMail`). 인코딩한 첨부 합계 + 본문이 `FORWARD_SIZE_BUDGET_BYTES`(40MB 에서 여유를 둔 35MB)를 넘으면 처음부터, 한도 안쪽인데 발송 API 가 크기 초과로 거절하면 한 번 더. 본문 속 이미지도 함께 빠지고 안내의 목록에 든다. 안내의 파일 이름은 응답자가 정한 글자라 HTML 이스케이프하고 줄바꿈을 걷어낸다. **첨부를 뺀 메일은 멱등 키가 다르다**(`reply-forward/<받은 메일 id>/no-attachments`) — 같은 키로 내용이 다른 요청은 거절된다. 크기 초과 거절의 오류 이름은 발송 서비스 문서에 없어 `isSizeRejection` 이 413 과 「크기를 말하는 검증 오류」 둘을 본다 — 실제 모양을 보면 그 함수 한 곳을 고친다.
- **장부의 이벤트 종류 칸**: `email.received:forwarded`(넘김) · `email.received:skipped`(넘기지 않음). 배포 전에 온 알림은 기존 경로가 `email.received` 그대로 적는다.
- **로그·오류 문구·Sentry 에 주소·이름·제목·본문을 싣지 않는다.** 발송 서비스가 돌려준 오류 문구도 주소를 담을 수 있어 분류값(`error.name`·상태 코드)만 옮긴다. 웹훅 라우트도 알림에 실린 주소·제목을 서비스에 넘기지 않는다.
- **배포**: 마이그레이션·Inngest Resync 없음. 앱 배포 뒤 Resend 웹훅 구독에 `email.received` 를 더한다.
